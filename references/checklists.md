# Pre-ship 打勾清單 + Part B 排查 + 症狀對照表

配合 SKILL.md 使用。**時機 2**（只加一個 endpoint / 頁面 / 背景工作）時，只跑對應那一張清單，不必全體檢。**Mode B**（已上線變慢）時，走 Part B。

---

## 四張 Pre-ship 清單

### A. 新增一個 API endpoint 前

- [ ] 回傳量隨什麼變數成長？有界嗎？（隨結果=好，隨表大小=危險）
- [ ] filter / sort / top-N / 聚合 / 去重 —— 全下推 DB 了嗎？
- [ ] 只 SELECT 用得到的欄？（沒有 `SELECT *` 拖大 JSON/長文字欄）
- [ ] 如果加了 cache：TTL / Eviction / Cap / Key 空間有界 —— 四問都答得出來嗎？
- [ ] 貴重計算有 in-flight 去重嗎？（50 個同時 miss 不會重算 50 次）
- [ ] 使用者輸入決定的工作量有 clamp 嗎？（天數 / 批次 / 每頁上限）
- [ ] 回傳 payload = 「UI 真正需要的量」而非「有的全部」？
- [ ] 改既有 endpoint：會不會破壞其他消費者對舊行為的假設？

### B. 新增一個前端頁面 / 元件前

- [ ] 用共用抓取層，還是各元件各抓 raw fetch？
- [ ] 輪詢頻率對得上資料實際更新率？（別 30 秒輪一份 30 分才變的資料）
- [ ] 每個 timer / listener / in-flight 請求，unmount 時都清掉了嗎？
- [ ] 切到背景分頁，輪詢會暫停嗎？
- [ ] 搜尋 / modal / 詳情資料：「打開才抓」還是總是抓？
- [ ] Loading / 成功 / 失敗 / 無資料 —— 四態誠實分清楚了嗎？（沒有假綠/假 0）

### C. 新增一個背景 / 排程工作前

- [ ] 單輪耗時多久？可能超過它的觸發間隔嗎？
- [ ] 有重疊保護嗎？（「上一輪還在跑就跳過」——一個 flag 就夠）
- [ ] 背景 + 使用者請求會觸發同一個計算嗎？有共享去重嗎？
- [ ] 失敗時保留舊狀態、不污染結果？
- [ ] 「同一時刻最多幾份在跑？」—— 這個數字有被明確控制嗎？（不能是「無上限」）
- [ ] 有單一實例鎖嗎？（避免上一輪沒結束、下一輪又起——例如用檔案鎖 flock/fcntl）
- [ ] 產出檔案（output/*.json、log）有 retention 嗎？

### D. 無人值守工作的死機告警 —— 改到排程 / 執行 / 背景程式後

> **條件清單：只在系統要「沒人看著自己跑」時跑，尤其是失敗會造成實際損失的那種。** 死機告警（dead man's switch：程式每輪跑完主動 ping 一個外部服務，太久沒 ping 就通知你）是無人值守的最後一道防線，而它可能被**無關的改動悄悄弄斷**——甚至更糟，弄成「報假平安」。任何動到排程 / 執行 / 背景程式的改動，收尾都補跑這張。

- [ ] **鏈路實測**：改完部署後，**手動跑一次** → 確認外部監控真的變綠、通知管道沒亂叫（30 秒的事，每次大改都做）
- [ ] **「報假平安」防呆**：平安 ping 只在**真正成功結束**時送，失敗走失敗端點？（最危險的改法 = 例外被吃掉卻還跑到結尾報平安 → 你以為它好的，其實壞了，比完全沒告警更糟）
- [ ] **設定還在**：告警用的環境變數還在排程設定裡嗎？（換過 crontab / 搬過專案目錄後尤其要確認 —— 值掉了通常只是靜默關閉：程式讀到空字串就跳過，不會報錯）
- [ ] **告警參數合理**：監控的 Period / Grace 對得上實際排程頻率嗎？（改了排程間隔記得回頭調監控設定，否則會一直誤報或永遠不報）
- [ ] **不可逆副作用**：這個工作會不會產生無法回收的外部動作（下單、付款、寄信、刪資料）？若會，另外準備一張該領域自己的安全清單——本 skill 只管「跑不跑得動、活不活得久」，不涵蓋領域風險。

## Part B｜已上線排查手冊（Mode B）

心法：**先量再猜，數字先於假設。別猜、別怪最近的 commit —— 找隨時間長大的東西（資料、cache 條目、記憶體）。**

### 步驟 0｜先給症狀分類

| 症狀 | 根因家族 | 下一步 |
|---|---|---|
| 單一 API 慢，其他正常 | 撈太多 / 沒下推 | 步驟 1–2；第 1–2 章 |
| 整站慢，連簡單頁都慢 | 進程層（記憶體/CPU） | 步驟 3；第 3–5 章 |
| 越跑越慢，重啟後好、幾天又慢 | 資源累積（記憶體/連線/cache） | 步驟 3；第 3–4 章 |
| 突然崩，沒改 code | 資料成長撞門檻 | 步驟 6；第 1 章 |
| 在某頁，別頁的資料還在抓 | 前端全域輪詢 / 無共用 cache | 步驟 5；第 7 章 |
| 回應巨大，頁面只顯示一點 | over-fetch | 步驟 4；第 6 章 |
| 畫面顯示正常但其實沒資料 | 狀態不誠實 | 第 8 章 |

### 步驟 1｜回應時間 —— 由外而內分段量
瀏覽器 → CDN/Proxy → 後端 → DB，逐段量。基準用「無 DB 無 auth 的 health-check」：health-check 也慢 → 進程層（記憶體/CPU/連線池耗盡）；health-check 快、業務慢 → 那個 endpoint 本身。找到慢 endpoint 後，立刻量它的 **DB 回傳列數**，多半直指第 1–2 章。

### 步驟 2｜Cache
- 同請求打第二次有變快嗎？沒有 → cache 沒作用或不存在。
- cache key 筆數隨使用者輸入成長嗎？會 → 潛在洩漏。
- 命中率低 → TTL 太短，或 key 設計每次都產新 key。

### 步驟 3｜記憶體
RSS 隨時間：長升不降 → 疑洩漏/無上限累積（再驗 heap used、heap snapshot、cache 條目數、GC 曲線）；鋸齒 → 撞頂重啟。本機重現：限記憶體上限 + 灌真實流量，舊 code 撞頂崩、修好的不崩 = 驗證。盤點所有比「單一請求」長命的結構，逐一檢查「出場」機制。

### 步驟 4｜Payload / 分頁
量每個 endpoint 回應 bytes，比對該頁實際顯示量。「回幾百 KB、頁面顯示 20 筆」= over-fetch，要分頁（第 6 章）。

### 步驟 5｜前端網路行為
開 DevTools Network：同 API 幾個並發請求（多 = 無共用抓取層）？輪詢頻率合理嗎（比對資料更新率）？切背景分頁有停嗎？切別頁舊 timer 停了嗎？

### 步驟 6｜資料成長
關鍵表現在幾列？每日成長率？「撈整表」的查詢估現在與 3 個月後的成本。append-only 表 retention 在跑嗎？

### 步驟 7｜心法總結
先量。每個假設都用數字驗：回傳列數、payload KB、latency 秒、RSS bytes。「沒改 code 卻突然壞」= 找隨時間長大的東西，別怪最近的部署——時間點對不上那個理論。
