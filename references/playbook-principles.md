# Playbook 通則（濃縮）— ship-check 的知識底層

濃縮自一份 web 效能 playbook 的通則部分（8 章）。每章：**核心原則 → 一句判準 → 自問清單**。運行 ship-check 時，對照 SKILL.md 的 7 個維度回來查這裡的細節。

核心心法貫穿全書：**先量再猜（measure before guessing）、會長大的變數（data / cache 條目 / 記憶體 / 連線都會隨時間長）、成本要是 O(結果大小) 而非 O(表大小)。**

---

## 第 1 章｜資料量是一個會長大的變數

**核心**：開發資料永遠追不上正式環境；成本隨「表大小」而非「結果大小」成長的操作，是隱形負債。「沒改 code 卻突然爆」= 資料成長撞到門檻。**append-only 表（事件記錄、價格快照、log、history）長最快、最危險，必須有明確 retention。**

**判準**：這個查詢回傳量，是隨結果大小（安全）還是隨表大小（危險）成長？

**自問**
- 撈的量隨結果還是隨表長？
- 計算能不能留在資料源（DB）做，而不是搬到程式端？
- append-only 表 3 個月後幾列？那時這查詢還跑得動嗎？有 retention 契約嗎？

**反模式**：撈全部再算 / 無上限的歷史查詢 / 列表頁不分頁只顯示前 20。

**實戰**：某儀表板的一個 endpoint 撈整張報價表（一個月內 9 萬 → 26.8 萬列），回 26.8 萬列只為顯示 27 筆，查詢 7 秒 → 把「每項取最新」下推 DB，回 27 列、100ms。

---

## 第 2 章｜計算下推：資料搬運是最貴的事

**核心**：搬資料有四種成本（網路傳輸、反序列化、記憶體 materialize、GC 暫時物件），不是一種。N+1 是同一種病的變體。

**判準**：是不是「撈一大袋原料，只為在程式裡挑一小把」？

**自問**
- filter / sort / top-N / 聚合 / 去重 —— 有沒有下推 DB？
- 有沒有用批次介面（`IN (...)`、批次讀、multicall）把 N+1 壓成 1？
- 有沒有只 SELECT 用得到的欄？（別 `SELECT *`，尤其有 JSON blob / 長文字大欄時）

**實戰**：同一個儀表板有多個 endpoint「撈全部歷史再用程式挑每項最新」→ 下推後回傳列數從上萬變數十；外部來源的逐筆讀取全改成批次呼叫。

## 第 3 章｜記憶體是一條不會自己變短的帳

**核心**：後端進程長命（跑數天數週），沒釋放的記憶體會累積。兩種不同失效：
- **Spike（尖峰）**：單一請求拉太多（整張表、巨大 API 回應），請求結束會回收，但高並發下會疊。
- **Leak（洩漏）**：資料放進比請求長命的結構（模組層 Map、全域 array、closure 捕獲），單調上升，只有重啟才歸零。

GC 救不了你：全域結構持有參照 = GC 認定「還在用」。洩漏的本質是「不小心永久持有」，不是「忘了釋放」。

**隱形洩漏樣板**：用**使用者輸入當 key** 的 cache（user id / 任意識別碼 / 時間範圍）且從不刪 —— key 空間無界，即使每筆很小，**筆數**也無上限成長。

**Lazy TTL 的假保護**：「讀時檢查過期就重算」聽起來安全，但過期項**還留在 Map 裡**只是不被讀 —— 記憶體從不下降。必須明確刪除。

**判準**：每個比「單一請求」長命的結構，都要有明確的「出場」機制（淘汰最舊 / TTL+真刪 / key 空間有界）。

**自問**
- 這結構的 key 空間能不能一句話講清楚？（「10 種固定項目」有界=安全；「使用者查的任意字串」無界=要上限+淘汰）
- 每個前端 `useEffect` 有沒有在 cleanup 清掉 timer / listener / abort？
- RSS 隨時間可觀測嗎？長升不降=疑洩漏；鋸齒=撞頂重啟。

**假死（thrash 非 crash）**：逼近上限時進程不崩，而是進入 GC thrash —— CPU 都在 GC，每個請求都慢，連不碰 DB 的 health-check 都 timeout。比崩潰更難診斷，看起來像「查詢慢」其實根因是記憶體。

## 第 4 章｜Cache 是拿記憶體換時間的交易

**核心**：cache 是交易（記憶體換速度、新鮮度換回應），不是免費加速。常見失效：cache 洩漏（第 3 章）、cache stampede（熱資料剛過期，50 個請求同時 miss、同時重算）、stale 靜默不一致。

**四問（缺一不可）**
1. **TTL（活多久）**：多久算過期？應由「底層資料實際多久變一次」推，不是隨手填。
2. **Eviction（誰刪）**：誰、何時真的刪過期項？（不讀 ≠ 刪 = 洩漏）
3. **Cap（上限幾筆）**：記憶體/筆數絕對上限？滿了淘汰誰？
4. **Key 空間有界性**：key 空間有限還無限？無限 → 必須配 cap + 淘汰。

**Stampede 根因**：沒有 in-flight 去重。第一個請求開始貴重計算，後 N 個應共享它的結果；沒去重就是 N 份平行重算。設計自問：「50 個請求在 cache 剛過期時湧入，會怎樣？」答「重算 50 次」= 要去重。

**Stale-on-error**：重算失敗可回舊值並標記 stale，**但**要設最大 stale 年齡，超過就回「無資料/失敗」而非無限撒謊。

## 第 5 章｜並發與背景工作：同時最多有幾份在跑？

**核心**：並發必須明確設界；不設界就會吃光記憶體與連線。`setInterval` 語意是「固定時間間隔觸發」，不是「上一輪跑完再等 X」——若一輪 25 分而 timer 每 20 分，就會重疊。

**判準**：「同一時刻最多幾份在跑？」的答案必須是明確數字，不能是「無上限」。

**自問**
- 背景 timer 有沒有重疊保護（「上一輪還在跑就跳過這次」）？一個 boolean flag 就夠。
- 背景路徑 + 使用者請求路徑會不會觸發同一個貴重計算？有沒有共享 in-flight 去重？
- 使用者輸入決定的工作量有沒有 **clamp**？（查詢範圍→最大天數；批次→最大筆數；分頁→每頁上限）。設計自問：「使用者輸入極端值，這工作會變多大？」
- 失敗時保留舊狀態、不污染結果？

**實戰**：某儀表板的背景工作每 20 分重算、單輪 3–6 分、無去重無重疊保護；上游一慢單輪 >20 分，下次 tick 照觸發 → 多輪疊 + cache 洩漏 = OOM 假死。修法：背景與請求收斂成單一入口 + 共享去重；timer 加「執行中」flag；某查詢 clamp 到最多 180 天。

## 第 6 章｜Payload 應該等於「UI 真正需要的量」

**核心**：回傳應是「UI 實際顯示的量」，不是「DB 有的全部」。over-fetch 四重成本：DB 撈沒用的列、後端 materialize、網路傳整包、瀏覽器 parse 並持有巨大 JSON。

**判準**：回傳量 = 這個畫面真正同時顯示的量？

**自問**
- 列表有沒有設計分頁介面（limit/offset 或 cursor）？頁大小 = 「螢幕同時顯示幾列」，不是「表裡幾列」。
- 「哪些列、什麼順序」的邏輯有沒有放後端？前端只顯示後端切好的頁。
- 改既有 endpoint 時，有沒有別的消費者依賴舊的「回全部」行為？（樣板：有分頁參數就用、沒有就維持舊全量 → 漸進遷移）

**實戰**：某 endpoint ~222KB/次、頁面顯示前 20 → 加分頁降到 ~22KB（10 倍）；「無參數→回全量（舊的全域搜尋要用）、有參數→前 20」兼顧不破壞依賴。

## 第 7 章｜前端資料抓取是「全域資源問題」，不是元件的私事

**核心**：沒有共用抓取層，N 個要同資料的元件 = N 個請求（必然重複）。輪詢的價值上限 = 資料的實際更新頻率；更快只是浪費。看不見的資源（背景分頁、離開的頁、沒開的 modal）不值得花資源抓。

**判準**：同一個 API 被幾個來源同時抓？輪詢頻率對得上資料更新率嗎？

**自問**
- 用共用抓取層（cache / request 去重）還是各元件各抓？
- 輪詢頻率是不是遠快於資料實際變動、卻沒意義？（資料 30 分變一次，前端每 30 秒輪 = 99% 抓到一樣的）
- 切到背景分頁會暫停輪詢嗎？離開頁面 timer 有清嗎？
- 常駐 UI（側邊狀態燈、header 健康指示）有沒有為了一個小燈去抓整份列表？→ 應由後端給**輕量 summary endpoint**（只回結論，~170–300 bytes；鐵律：只讀現成資料、絕不觸發貴重重算、沒好就誠實說沒有）。
- 搜尋框 / modal / 詳情：打開才抓，還是總是抓？

## 第 8 章｜誠實狀態與版本落差

**核心**：Loading / 成功 / 失敗 / 無資料 是**四個不同狀態**，不可互換。最糟反模式：資料缺失/失敗時 UI 顯示「預設正常值」（綠燈、0、空白）→ 使用者以為系統健康，其實根本沒資料。前後端分開部署 → 必有「新前端配舊後端」的短暫版本落差，要優雅降級而非顯示壞掉。

**判準**：抓不到這份資料時，畫面是誠實說「抓不到」，還是假裝「一切正常」？

**自問**
- Loading / 成功 / 失敗 / 無資料 有沒有分開顯示？失敗 ≠ 無資料 ≠ 成功。
- endpoint 不存在 / 欄位缺失時，前端有沒有優雅降級（顯示「未知/灰/載入中」而非假綠、也不是紅色錯誤）？
- 懂不懂部署順序造成的版本落差窗口？寫了容忍邏輯嗎？

**實戰**：preview（新前端）配尚未部署的後端，側邊燈顯示灰（連不到還不存在的 summary endpoint）—— 這是**正確行為**：誠實說「無資料（灰）」而非假綠；後端部署後燈變綠。誠實狀態 + 優雅降級的範例。
